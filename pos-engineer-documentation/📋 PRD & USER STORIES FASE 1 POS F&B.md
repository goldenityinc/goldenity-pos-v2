📋 PRD & USER STORIES: FASE 1 POS F&B REBUILD (V2)Dokumen Referensi untuk Sinkronisasi ClickUp & Test Case Generation oleh Claude1. Executive SummaryFase 1 dari Rebuild V2 ini berfokus murni pada fondasi Backend dan POS Native (Flutter) untuk operasional Food & Beverage (F&B) end-to-end. Sistem Web Order dan Bridge (Socket.IO) secara eksplisit dikeluarkan dari cakupan fase ini untuk memastikan inti aplikasi kasir berjalan dengan stabilitas 100% tanpa risiko freeze atau technical debt.  Arsitektur database dan logika bisnis akan mengadopsi 100% struktur dari V1 (seperti tenantSlug, tabel products, dan format cetak ESC/POS) yang sudah terbukti andal di produksi, dengan peningkatan arsitektural pada sisi POS Flutter (Riverpod state management, komponen UI yang dapat digunakan kembali, dan sinkronisasi antrean offline).  2. Epics & User Stories (Format ClickUp)EPIC 1: Auth JWT & Multi-Tenant CoreTujuan: Mengamankan akses sistem dengan JWT berbatas waktu (24 jam) dan menerapkan isolasi data antar cabang secara ketat (RBAC).  Story 1.1: Backend - Multi-Tenant Login EndpointDeskripsi: Sebagai pengguna, saya ingin login menggunakan tenantSlug (kode perusahaan), username, dan password agar saya bisa mengakses data spesifik milik perusahaan saya.  Acceptance Criteria (AC):Sistem memvalidasi tenantSlug terlebih dahulu.  Sistem mengembalikan token JWT dengan payload memuat userId, tenantId, branchId, dan role.  Password harus dienkripsi dengan bcrypt (mendukung fallback teks biasa sementara untuk migrasi).  Story 1.2: POS Native - Session Persistence & RestoreDeskripsi: Sebagai kasir, saya ingin sesi login saya tersimpan secara lokal (selama < 24 jam) sehingga saya tidak perlu login berulang kali saat aplikasi ditutup dan dibuka kembali.  AC: Token JWT dan metadata pengguna disimpan di SharedPreferences. Jika lebih dari 24 jam, sistem otomatis memaksa logout (tidak boleh silent fail).  Story 1.3: Backend - RBAC & Branch Isolation LogicDeskripsi: Sebagai kasir, saya hanya boleh melihat dan memproses data (produk, transaksi) yang berada di cabang saya sendiri.  AC: Middleware resolveEffectiveBranchFilter harus diimplementasikan. Role CASHIER tidak boleh mem- bypass filter cabang meskipun mereka memanipulasi parameter URL.  EPIC 2: Manajemen Inventaris & Kategori (F&B)Tujuan: Memungkinkan POS mengelola daftar menu secara offline-first dengan resolusi nama kategori berbasis string untuk meminimalisir kegagalan sinkronisasi.  Story 2.1: Backend - Category CRUD & Soft DeleteDeskripsi: Sebagai Admin, saya dapat menambah, mengubah, dan menghapus kategori produk (misal: "Minuman", "Makanan Utama").  AC: Nama kategori harus unik per tenantId. Saat menghapus, gunakan metode soft-delete jika kategori masih digunakan oleh produk.  Story 2.2: Backend - Product CRUD dengan Auto-Create CategoryDeskripsi: Sebagai sistem sinkronisasi, ketika saya menerima data produk baru dari POS yang memiliki kategori belum terdaftar, kategori tersebut harus dibuat otomatis.  AC: Endpoint mendukung pembuatan kategori otomatis berdasarkan pencocokan nama string case-insensitive.  Story 2.3: POS Native - 3-Tier Fallback Cascade FetchDeskripsi: Sebagai kasir dengan koneksi internet tidak stabil, aplikasi harus tetap bisa mengunduh daftar produk dengan mencoba berbagai rute API secara berurutan.  AC: POS menerapkan mekanisme 3 tingkat cadangan saat mengambil /api/v1/products.  Story 2.4: POS Native - Local Cache & Sync Queue (Hive)Deskripsi: Sebagai kasir, saya bisa membuat menu baru saat offline, dan data tersebut akan otomatis dikirim ke server saat internet kembali tersambung.  AC: Penyimpanan lokal menggunakan Hive (local_products, local_categories, pending_sync_queue). Antrean cadangan (sync queue) diproses setiap 30 detik di latar belakang.  EPIC 3: Alur Penjualan (Sales & Checkout)Tujuan: Memastikan perhitungan keranjang (subtotal, diskon, pajak) akurat dan menghasilkan struktur data transaksi (reference_id) yang andal meskipun diproses saat offline.  Story 3.1: POS Native - Deduplikasi Item KeranjangDeskripsi: Saat saya menekan menu yang sama berulang kali, jumlah (qty) item tersebut di keranjang harus bertambah, bukan membuat baris baru.  AC: Logika pencocokan berurutan: id -> barcode -> name.  Story 3.2: POS Native - Perhitungan PPN DinamisDeskripsi: Sebagai toko yang memungut pajak, perhitungan PPN harus dinamis berdasarkan aturan apakah harga sudah termasuk pajak ( include ) atau belum ( exclude ).  AC: Menggunakan formula pembalik total / (1 + rate/100) * (rate/100) jika harga include pajak. Data konfigurasi pajak harus selalu dibaca dari status terkini (bukan cache yang kedaluwarsa).  Story 3.3: POS Native - Komponen Pembayaran (CashTender & PaymentCard)Deskripsi: Sebagai kasir, saya membutuhkan komponen antarmuka yang seragam untuk memproses pembayaran tunai dan non-tunai di seluruh bagian aplikasi.  AC: Komponen GoldenityCashTenderModal dan GoldenityPaymentCard wajib dibangun secara terpusat di lib/shared/widgets/ untuk menghindari duplikasi kode.  Story 3.4: Backend - 5-Step Atomic Transaction (Create Sale)Deskripsi: Saat menyimpan transaksi, sistem harus memastikan pembayaran, inventaris (pengurangan stok), dan log tercatat secara serentak (atomik) untuk mencegah data parsial.  AC: Penggunaan Prisma $transaction. Membutuhkan snapshot nama produk secara permanen (product_name) untuk mencegah kerusakan data struk jika produk dihapus di masa depan. Transaksi utama diidentifikasi dengan reference_id dari POS untuk mencegah duplikasi.  EPIC 4: Printer & Pengaturan Perangkat KerasTujuan: Mendukung pencetakan ganda (Kasir & Dapur) menggunakan perangkat ESC/POS yang berbeda dengan resolusi jeda waktu perangkat keras.  Story 4.1: POS Native - 3-Slot Printer ResolverDeskripsi: Sebagai merchant, saya bisa mengatur satu printer utama ( default ), namun saya juga punya opsi untuk memisahkan printer khusus Dapur dan Kasir jika dibutuhkan.  AC: Logika cadangan: Jika slot Dapur atau Kasir tidak diatur, otomatis dialihkan (fallback) ke slot Default.  Story 4.2: POS Native - Jeda Waktu Cetak (Fix Buffer Overflow)Deskripsi: Saat mencetak struk panjang atau berlogo, printer tidak boleh terputus ( hang ) di tengah jalan.  AC: Menerapkan jeda paksa 450ms antara pengiriman data logo (Job 1) dan teks struk (Job 2), serta jeda serupa antar tiket dapur (INV #2A fix).  3. Catatan Khusus untuk Claude (Test Case Generation)Saat Anda (Claude) menghasilkan Test Cases di ClickUp untuk cerita pengguna ( User Stories ) di atas, Anda WAJIB menyertakan Skenario Negatif untuk mencegah 5 Anti-Pattern yang ditemukan di V2 lama:  Uji Duplikasi File: Pastikan tidak ada dua file yang mengontrol pengaturan layar yang sama.  Uji Duplikasi Komponen: Verifikasi bahwa komponen seperti modal uang tunai (cash tender) dipanggil dari lib/shared/widgets/, bukan dibuat ulang.  Uji Timpa Status Sepihak (Silent Overwrite): Verifikasi bahwa pembaruan data internal dari Riverpod tidak mereset status UI (seperti toggle pajak) tanpa persetujuan pengguna (wajib ada pemeriksaan kesetaraan/ equality check).  Uji Konsistensi Nama Variabel (Snapshot): Verifikasi bahwa penamaan produk pada keranjang dan struk hanya menggunakan satu atribut absolut (misalnya productName), tanpa mengandalkan skema fallback multi-nama (rawProductName dll).  Uji Status Memuat (Loading State): Pastikan layar pengaturan tidak pernah menggunakan status default bawaan selama pemuatan awal dari server.
